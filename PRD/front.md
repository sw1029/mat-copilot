## 1. 개요 (Overview)
mat-copilot은 대화형 AI 에이전트가 사용자의 초기 아이디어를 한 번에 하나씩 질문하여 구체화하고, 답변을 바탕으로 PRD를 생성한 뒤(기술 개요가 필요하다고 백엔드가 판단한 경우 TRD도 함께 생성), 사용자가 제출한 최종 결과물과 문서 사이의 의도 왜곡, 요구사항 누락 및 할루시네이션을 분석·시각화하는 서비스다.

프론트엔드가 다루는 입력은 세 가지다.
1. (선택) 기존에 작성한 계획 문서(docx/txt/md) — 업로드 시 백엔드가 전처리하여 분석 기준으로 저장한다.
2. (필수) 유저 채팅 — 한 번에 하나씩 제시되는 질문에 대한 답변 루프.
3. (필수) 최종 결과물 — 질의 종료 후 링크(웹 페이지/GitHub) 또는 파일(zip/docx/문서/코드)로 제출.

프론트엔드가 표시하는 출력은 백엔드가 작성해 넘겨주는 것을 그대로 렌더링한다.
1. PRD(프로젝트 개요 문서) — 항상 생성되며 문서 패널 상단에 표시한다.
2. (선택) TRD — 기술 개요가 필요한 경우에만 백엔드가 생성하며 문서 패널 하단에 표시한다. 표시/비표시는 백엔드 응답에 TRD가 포함되는지를 기준으로 결정한다.
3. 차이 상세 리포트 — 백엔드가 넘겨주는 비교·지표·리포트 데이터를 받아 그대로 렌더링한다.

프론트엔드는 React 기반의 전체 화면 고정형 웹 애플리케이션으로 구성한다. 사용자는 캔버스 전체가 아닌 질문 카드가 배치된 챗봇 영역만 드래그하여 질문 흐름을 탐색한다. 질문은 백엔드가 반환하는 수만큼 동적으로 추가되며, 이전 질문과 다음 질문을 좌측에서 우측으로 연결한 마인드맵 형태로 표현한다.

핵심 화면 흐름은 `홈/첫 질문(+선택 문서 업로드) → 연속 질의 → 최종 결과물 제출 → 문서 생성 대기 → 분석 결과`의 다섯 단계다.

## 2. 배경 및 문제 정의 (Background & Problem)
- 현재 상황: 사용자의 초기 의도는 대체로 모호하며, AI를 활용해 문서나 코드를 생성하는 과정에서 요구사항 누락, 의미 변형, 불필요한 토큰 소비가 발생할 수 있다.
- 사용자 문제:
  - PRD와 TRD를 작성하기 위해 어떤 정보를 제공해야 하는지 알기 어렵다.
  - 여러 질문을 한 번에 받으면 답변 부담이 커지고, 중요한 맥락을 놓치기 쉽다.
  - 생성된 PRD와 TRD의 어떤 항목이 서로 대응하며 어디에서 차이가 생겼는지 빠르게 파악하기 어렵다.
  - 분석 점수만으로는 차이의 원인과 개선 방법을 이해하기 어렵다.
- 해결 방향:
  - 한 번에 하나의 질문만 제시하는 단계형 대화를 제공한다.
  - 누적된 질문 흐름을 드래그 가능한 마인드맵으로 시각화한다.
  - 문서 생성 및 분석 진행 상태를 명확히 안내한다.
  - PRD·TRD 원문, 대응 관계, 차이점, 종합 지표 및 상세 리포트를 하나의 결과 화면에서 연결해 보여준다.

## 3. 목표 및 비목표 (Goals & Non-Goals)
### 3.1 목표
- G1. 사용자가 별도 사용법 학습 없이 첫 질문에 바로 답변을 시작할 수 있게 한다.
- G2. 항상 한 번에 하나의 활성 질문만 제시하여 답변의 인지 부담을 낮춘다.
- G3. 백엔드가 반환하는 가변 길이의 질문과 분기 구조를 제한 없이 렌더링한다.
- G4. 사용자가 챗봇 영역을 드래그하여 전체 질의 맥락과 현재 위치를 쉽게 탐색하게 한다.
- G5. PRD 생성, TRD 생성(백엔드가 필요하다고 판단한 경우), 비교 분석의 진행 상태와 실패 여부를 투명하게 전달한다.
- G6. 결과 화면에서 PRD와 비교 대상(TRD 또는 최종 결과물)의 대응 항목 및 차이 위치를 각주 번호로 즉시 식별하게 한다.
- G7. 의도 정합성, 의도 왜곡도, 요구사항 누락 및 할루시네이션을 이해하기 쉬운 시각화로 제공한다.
- G8. 차이 항목 선택 시 원인, 영향도, 근거 및 개선 제안을 상세 리포트로 연결한다.
- G9. 사용자가 기존 계획 문서(docx/txt/md)를 선택적으로 업로드하여 전처리 후 분석 기준으로 활용하게 한다.
- G10. 인터뷰 종료 후 최종 결과물(링크 또는 파일)을 제출받아 의도 대비 drift 분석의 대상으로 삼는다.

### 3.2 비목표
- NG1. 프론트엔드에서 LLM 추론, 문서 비교 또는 토큰 산정 알고리즘을 직접 수행하지 않는다.
- NG2. MVP에서 PRD·TRD 전문 편집기, 실시간 공동 편집 또는 버전 관리 기능을 제공하지 않는다.
- NG3. MVP에서 사용자가 질문 노드를 임의로 생성·삭제하거나 연결선을 수정하는 기능은 제공하지 않는다.
- NG4. 프론트엔드가 분석 결과의 정확성을 자체 검증하거나 보정하지 않는다.
- NG5. 모바일 전용 레이아웃 및 네이티브 앱은 MVP 범위에 포함하지 않는다.

## 4. 사용자 및 이해관계자 (Users & Stakeholders)
| 구분 | 설명 | 프론트엔드에 대한 기대 |
| --- | --- | --- |
| 기획자/PM | 아이디어를 제품 요구사항으로 구체화하려는 사용자 | 적은 학습 비용, 명확한 질문 흐름, 읽기 쉬운 PRD 및 비교 결과 |
| 개발자/테크 리드 | PRD를 기술 요구사항으로 전환하고 정합성을 검토하는 사용자 | PRD·TRD 대응 관계, 누락·왜곡 근거, 구체적인 개선 제안 |
| AI 도구 사용자 | AI 산출물의 품질과 비용 효율을 확인하려는 사용자 | 신뢰 가능한 점수 설명, 할루시네이션·왜곡 지표 시각화 |
| 백엔드/AI 에이전트 팀 | 질문, 문서, 분석 데이터를 제공하는 팀 | 명확한 상태·오류 계약과 가변 데이터의 안정적인 렌더링 |
| 운영/관리자 | 서비스 품질과 장애를 관리하는 담당자 | 사용자 흐름별 오류 및 성능 관측 가능성 |

## 5. 정보 구조 및 핵심 사용자 흐름
### 5.1 전역 구조
- 화면은 브라우저 뷰포트 전체 크기로 고정하고 문서 본문 자체의 스크롤은 사용하지 않는다.
- 좌측 상단에는 모든 단계에서 식별 가능한 홈 버튼을 고정 배치한다.
- 각 화면 내부에서 필요한 영역만 독립적으로 스크롤하거나 드래그한다.
- 홈 버튼 선택 시 진행 중인 답변이 있으면 이탈 확인 모달을 표시하고, 확정 시 초기 화면으로 이동한다.

### 5.2 기본 흐름
1. 사용자가 홈 화면에 진입한다.
2. (선택) 기존 계획 문서(docx/txt/md)를 업로드하면 전처리 진행·완료 상태를 표시하고, 전처리 결과는 분석 기준으로 저장된다.
3. 첫 질문 카드와 답변 입력 영역이 표시된다.
4. 사용자가 답변을 제출하면 전송 중 상태를 표시하고 중복 제출을 방지한다.
5. 백엔드에서 다음 질문을 받으면 기존 노드 오른쪽에 연결선과 함께 새 질문 노드를 추가한다.
6. 새 질문을 활성화하고 필요한 경우 해당 노드가 보이도록 챗봇 캔버스 위치를 자동 보정한다.
7. 백엔드가 질의 종료를 반환할 때까지 4~6단계를 반복한다.
8. 질의가 끝나면 최종 결과물 제출 화면으로 전환한다.
9. 사용자가 결과물(링크 또는 파일)을 제출하면 백엔드가 TRD(기술 개요) 필요 여부를 판단하고, 문서 생성 및 분석 대기 화면으로 전환한다.
10. 모든 작업이 완료되면 결과 화면으로 자동 전환한다.
11. 사용자가 차이 각주 또는 시각화 항목을 선택하면 연관된 문서 구간을 강조하고 상세 리포트를 표시한다.

### 5.3 상태 흐름
`INITIAL → INTERVIEWING → SUBMITTING_ARTIFACT → GENERATING_PRD → (GENERATING_TRD: 백엔드가 필요 판단 시에만) → ANALYZING → COMPLETED`

오류 발생 시 현재 단계를 보존한 `FAILED` 상태로 전환하며, 사용자가 재시도하면 실패한 단계부터 이어서 수행한다.

## 6. 화면별 디자인 요구사항
### 6.1 화면 1 — 홈 및 첫 질문
- 좌측 상단에 서비스 로고 또는 홈 아이콘과 서비스명을 표시한다.
- 첫 질문 카드 상단에 선택형 계획 문서 업로드 영역을 표시한다.
  - docx/txt/md 파일을 받으며, 업로드는 선택 사항임을 명시한다.
  - 업로드 시 전처리 진행 중 상태(스피너·안내 문구)와 완료 상태(추출 요약)를 표시한다.
  - 업로드하지 않아도 인터뷰 진행에 제약이 없어야 한다.
- 화면 중앙 또는 시선이 먼저 도달하는 위치에 첫 질문 카드 하나만 표시한다.
- 질문 카드에는 다음 요소를 포함한다.
  - 현재 질문
  - 질문의 목적이나 답변 예시를 제공하는 보조 설명(데이터가 있는 경우)
  - 단일 또는 여러 줄 답변 입력 필드
  - 제출 버튼
- 답변이 비어 있거나 유효성 조건을 만족하지 않으면 제출 버튼을 비활성화하고 이유를 안내한다.
- 키보드 사용자는 입력 필드에서 단축키로 제출할 수 있어야 하며, 줄바꿈 입력과 제출 동작을 명확히 구분한다.

### 6.2 화면 2 — 연속 질의 마인드맵
- 질문 노드는 좌측에서 우측 방향으로 시간 순서 또는 백엔드가 제공한 연결 관계에 따라 배치한다.
- 각 연결선은 질문 간 선후·분기 관계를 나타내며, 방향을 인지할 수 있는 형태로 표현한다.
- 노드 상태를 시각적으로 구분한다.
  - 완료: 답변 제출이 끝난 질문
  - 활성: 현재 답변해야 하는 질문
  - 전송 중: 답변 처리 또는 다음 질문 생성 중
  - 오류: 제출 또는 질문 로드 실패
- 완료 노드에는 질문 요약과 답변 요약을 표시하되, 긴 내용은 말줄임 후 선택 시 전체 내용을 보여준다.
- 한 번에 하나의 노드만 활성화한다. 아직 도착하지 않은 질문을 미리 표시하지 않는다.
- 질문 개수와 깊이는 고정하지 않으며 백엔드 데이터에 따라 동적으로 추가한다.
- 챗봇 캔버스 동작:
  - 캔버스 또는 지정된 핸들을 포인터로 드래그하여 질문 흐름을 이동한다.
  - 전체 페이지와 전역 헤더는 이동하지 않는다.
  - 입력 필드의 텍스트 선택·스크롤 동작과 캔버스 드래그가 충돌하지 않아야 한다.
  - 캔버스 경계를 벗어나 노드를 영구히 잃어버리지 않도록 이동 범위 또는 위치 복원 기능을 제공한다.
  - `현재 질문으로 이동` 버튼을 제공한다.
  - 노드가 많아지면 축소·확대 또는 미니맵을 후속 단계에서 제공할 수 있다.
- 다음 질문 로딩 중에는 현재 흐름 끝에 스켈레톤 노드를 표시한다.
- 이전 답변 수정은 백엔드가 재질의를 지원하는 경우에만 제공하며, 수정 시 이후 분기가 재생성될 수 있음을 사전에 알린다.

### 6.2.1 화면 2.5 — 최종 결과물 제출
- 질의 종료 신호 수신 시 최종 결과물 제출 화면으로 전환한다.
- 결과물은 링크(웹 페이지/GitHub) 입력 또는 파일(zip/docx/문서/코드) 첨부로 제출한다.
- 링크와 파일 중 최소 하나가 있어야 제출 버튼이 활성화된다.
- 제출 중 상태를 표시하고 중복 제출을 방지한다.
- 제출 결과에 따라 백엔드가 TRD(기술 개요) 생성 필요 여부를 판단하며, 프론트엔드는 판단 결과를 대기 화면 단계 구성과 결과 화면 표시에 반영한다.

### 6.3 화면 3 — 문서 생성 및 분석 대기
- 대기 화면은 다음 단계를 순서대로 표시한다. TRD 생성 단계는 백엔드가 필요하다고 판단한 경우에만 포함되어 단계 수가 2~3개로 가변적이다.
  1. PRD 생성
  2. (조건부) TRD 생성 — 기술 개요 필요 판단 시
  3. PRD·(TRD·)결과물 비교 및 추론 결과 생성
- 각 단계는 `대기`, `진행 중`, `완료`, `실패` 상태를 아이콘과 텍스트로 함께 표현한다.
- 백엔드가 실제 진행률을 제공할 때만 백분율 진행률을 표시한다. 제공하지 않으면 확정되지 않은 임의 백분율 대신 단계형 로더를 사용한다.
- 장시간 작업 중에도 서비스가 멈춘 것으로 오해하지 않도록 현재 수행 작업과 경과 상태를 안내한다.
- 사용자가 새로고침하거나 재접속해도 작업 ID를 기반으로 최신 진행 상태를 복원한다.
- 실패 시 실패한 단계, 사용자에게 이해 가능한 오류 메시지, 재시도 버튼을 표시한다. 완료된 이전 단계는 반복 실행하지 않는다.

### 6.4 화면 4 — 분석 결과
#### 전체 레이아웃
- 데스크톱 기준 좌측 30%, 우측 70%의 2열 구조로 구성한다.
- 좌측과 우측 사이에는 명확한 구분선을 사용한다.
- 각 패널은 고정된 전체 화면 안에서 독립 스크롤한다.

#### 좌측 30% — PRD·TRD 문서 패널
- 상단에 PRD를 항상 표시한다.
- TRD는 백엔드 응답에 포함된 경우에만 하단에 표시한다. 미포함 시 하단에 `TRD 미생성 — 기술 개요가 필요하지 않음` 안내를 표시한다.
- TRD가 있는 경우 좌측 영역을 세로 50:50으로 나누고, 없는 경우 PRD가 영역 대부분을 사용한다.
- 각 문서 패널에 문서명, 생성 상태, 다운로드 버튼을 제공한다.
- Markdown 문서를 읽기 쉬운 서식으로 렌더링하되 원문 구조와 제목 계층을 보존한다.
- 서로 대응하는 구간(PRD ↔ TRD 또는 PRD ↔ 결과물)에 동일한 각주 번호를 부여한다.
- 차이가 있는 구간은 색상뿐 아니라 테두리, 아이콘 또는 밑줄로 함께 표시한다.
- 각주 선택 시:
  - 양쪽 문서의 대응 구간을 동시에 강조한다.
  - 선택된 구간이 보이도록 두 문서 패널을 각각 스크롤한다.
  - 우측 상단 시각화에서 관련 항목을 강조한다.
  - 우측 하단에 해당 차이의 상세 리포트를 표시한다.
- 분석상 대응 구간이 없는 누락 항목은 `한쪽 문서에만 존재` 상태로 구분한다.
- 선택된 각주 번호와 현재 선택 상태는 두 문서에서 일관되게 유지한다.

#### 우측 70% / 상부 40% — 종합 분석 시각화
- 다음 핵심 지표를 우선 제공하며, 백엔드가 넘겨주는 지표 목록을 그대로 렌더링한다.
  - 의도 정합성 점수
  - 의도 왜곡도
  - 요구사항 충족률 또는 누락률
  - PRD·TRD 항목 간 일치율 (TRD가 생성된 경우에만 포함)
  - 할루시네이션 지수
- 지표 카드는 한 화면에 모두 보이도록 단일 행 그리드로 배치하며, 상부 영역 안에서 드래그나 스크롤 없이 확인 가능해야 한다.
- 지표의 산식 또는 의미를 툴팁이나 정보 패널에서 확인할 수 있어야 한다.
- 상태 색상은 기본적으로 초록색을 양호, 빨간색을 주의/나쁨으로 사용하되 중간 상태는 중립색 또는 주황색으로 표현한다.
- 색상에만 의미를 의존하지 않고 점수, 라벨, 아이콘 및 패턴을 병행한다.
- 시각화 항목을 선택하면 대응하는 문서 각주와 상세 리포트를 함께 활성화한다.
- 데이터가 없거나 계산할 수 없는 지표는 0점으로 오인되지 않도록 `산정 불가`와 사유를 표시한다.

#### 우측 70% / 하부 60% — 차이 상세 리포트
- 리포트 내용은 백엔드가 넘겨주는 데이터를 그대로 렌더링하며, 프론트엔드는 가공하지 않는다.
- 기본 상태에서는 각주 선택 방법과 분석 요약을 안내한다.
- 항목 선택 시 다음 정보를 표시한다.
  - 각주 번호 및 항목 제목
  - 상태: 일치, 부분 일치, 왜곡, 누락, 추가
  - 차이 요약
  - 차이라고 판단한 근거
  - 원래 의도에 미치는 영향과 심각도
  - PRD 인용문 및 비교 대상(TRD 또는 결과물) 인용문
  - 개선 제안
  - 분석 신뢰도(백엔드가 제공하는 경우)
- 긴 리포트는 하부 패널 안에서 독립적으로 스크롤한다.
- 문서 내 관련 위치로 이동할 수 있는 액션을 제공한다.

### 8.1 프론트엔드 데이터 계약 개요
상세 엔드포인트와 스키마는 TRD에서 확정하며, 프론트엔드는 최소한 다음 데이터를 필요로 한다.

| 데이터 | 필수 필드 예시 | 사용 목적 |
| --- | --- | --- |
| 인터뷰 세션 | `sessionId`, `status`, `createdAt` | 질의 상태 저장 및 복구 |
| 계획 문서 업로드 | `documentId`, `fileName`, `preprocessStatus`, `extractedSummary` | 선택 업로드 및 전처리 상태 표시 |
| 질문 노드 | `questionId`, `parentId`, `prompt`, `helperText`, `inputType`, `validation`, `status` | 동적 마인드맵 렌더링 |
| 답변 | `questionId`, `value`, `submittedAt` | 노드 완료 상태 및 답변 요약 |
| 결과물 제출 | `artifactId`, `type(link/file)`, `value`, `needsTrd` | 최종 결과물 제출 및 TRD 생성 여부 판단 결과 수신 |
| 생성 작업 | `jobId`, `stages`(가변), `stage`, `status`, `progress`, `error` | 대기 화면 및 재시도. TRD 단계 포함 여부는 백엔드 판단 |
| 생성 문서 | `documentId`, `type`, `title`, `markdown`, `downloadUrl` | 문서 렌더링 및 다운로드. TRD는 응답 포함 시에만 존재 |
| 대응 구간 | `comparisonId`, `footnoteNumber`, `prdRange`, `targetRange`, `status`, `severity` | 각주 및 교차 강조 |
| 분석 지표 | `metricId`, `label`, `value`, `unit`, `threshold`, `status`, `description` | 상부 시각화 (백엔드 목록 그대로 렌더링) |
| 상세 분석 | `comparisonId`, `summary`, `reason`, `impact`, `prdQuote`, `targetQuote`, `recommendation`, `confidence` | 하부 리포트 (백엔드 데이터 그대로 렌더링) |

| 해상도 | 데스크톱 1440×900을 기준으로 설계하며 최소 1280×720에서 핵심 기능을 유지한다. |

## 11. 제약 및 가정 (Constraints & Assumptions)
### 11.1 제약
- React 기반 웹 애플리케이션으로 구현한다.
- 화면 전체는 고정하며 질문 탐색을 위한 챗봇 캔버스만 드래그할 수 있다.
- 질문 개수는 프론트엔드에서 제한하거나 사전 가정하지 않는다.
- PRD 생성, TRD 생성 여부 판단, 비교 분석 결과는 백엔드가 제공하며 프론트엔드는 그대로 렌더링한다.
- 결과 화면의 기본 비율은 좌측 30%, 우측 70%이며 우측은 상부 40%(지표), 하부 60%(상세 리포트)다.
- 우측 상부의 지표 카드는 스크롤 없이 한 화면에 모두 표시한다.

### 11.2 가정
- 백엔드는 각 질문의 고유 ID, 부모 관계 및 종료 여부를 일관된 형식으로 제공한다.
- 문서 비교 결과에는 양쪽 문서의 안정적인 위치 식별자 또는 범위 정보가 포함된다.
- 분석 지표에는 값뿐 아니라 상태 기준, 단위 및 설명이 포함된다.
- 생성 작업은 비동기로 수행되며 작업 ID를 통해 상태를 재조회할 수 있다.
- 분석 결과가 완료된 이후에도 동일 세션 ID로 다시 접근할 수 있다.

## 14. 수용 기준 (Acceptance Criteria)
1. 첫 진입 시 첫 질문 하나와 답변 입력 요소, 선택형 계획 문서 업로드 영역만 표시된다.
2. 답변 제출 후 백엔드가 반환한 다음 질문이 기존 질문 오른쪽에 연결되어 표시된다.
3. 질문 개수가 사전에 정해지지 않아도 모든 반환 질문을 렌더링할 수 있다.
4. 사용자는 페이지 전체가 아닌 챗봇 캔버스만 드래그할 수 있다.
5. 입력 필드 조작과 캔버스 드래그가 충돌하지 않는다.
6. 질의 종료 후 최종 결과물 제출 화면이 표시되고, 제출 후 PRD 생성 → (조건부) TRD 생성 → 분석 단계가 순서대로 표시된다.
7. 새로고침 후에도 진행 중 작업 또는 완료 결과가 복구된다.
8. 결과 화면은 데스크톱에서 좌측 30%, 우측 70% 구조를 유지하며 우측은 상부 40%, 하부 60%로 나뉜다.
9. TRD가 생성된 경우 좌측 PRD·TRD 패널은 세로로 나뉘어 각각 독립 스크롤되고, 미생성 시 TRD 자리에 미생성 안내가 표시된다.
10. 동일 비교 항목은 PRD와 비교 대상에서 동일한 각주 번호로 표시된다.
11. 각주 선택 시 양쪽 문서 구간, 관련 시각화 및 우측 하단 리포트가 동기화된다.
12. 양호·주의 상태는 색상을 보지 않아도 텍스트나 아이콘으로 구분할 수 있다.
13. 실패한 질문 제출 시 사용자의 입력값이 유실되지 않는다.
14. 생성 또는 분석 실패 시 완료된 단계는 유지되고 실패 단계만 재시도할 수 있다.
15. 키보드만으로 첫 질문 답변부터 결과 상세 리포트 탐색까지 핵심 흐름을 수행할 수 있다.
16. 우측 상부의 지표 카드는 스크롤이나 드래그 없이 모두 확인할 수 있다.
